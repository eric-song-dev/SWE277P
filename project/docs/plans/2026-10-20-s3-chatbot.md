# S3: Chatbot and LLM Profiles Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The backend chatbot, end to end:

- encrypted LLM profiles with test connection;
- a custom LangGraph text-to-SQL graph with clarification, repair, and optional result analysis;
- the SQL guard and the read-only executor;
- a streamed SSE API, conversations, and chat-result export;
- a benchmark runner with 20 questions.

The privacy (A6) and harmful-SQL (A8) acceptance tests pass.

**Architecture:** `chat/graph/` holds a per-request `StateGraph` with no checkpointer. History comes from `chat_turn`. Nodes emit UI events through LangGraph's custom stream writer, and the service turns them into SSE. Every LLM call goes through one `ChatOpenAI` factory, plus a scripted fake model for tests and demos.

**Tech Stack:** S2 stack plus langgraph 1.2, langchain-core 1.6, langchain-openai 1.7, sqlglot 30. Dev group: pandas, pyyaml, pytest-asyncio 1.4.

**Spec:** `project/docs/specs/2026-10-20-data-hub-design.md` (Sections 2, 7, 8, 13, 14). S2's plan (`2026-10-20-s2-foundation-import.md`) defines the interfaces used here.

## Global Constraints

- Every S2 global constraint still applies: paths relative to `project/`, commit rules, error shape, `get_current_user` on every route.
- **The generate prompt never contains row values.** It contains only:
  - the view description and domain rules;
  - controlled values (distinct `school`, `event_name`, `event_type`, `term`, `academic_year`, `affiliation`);
  - history (prior `question`, `sql`, `interpretation`, `row_count`, `clarification_question`);
  - sanitized repair feedback;
  - the question.
- **The analyze prompt is the only place rows appear.** It runs only when the profile has `share_results_with_llm = true` and the request has `share_results = true` (spec D2). The server computes this, so the request alone never turns sharing on. It gets at most `LLM_RESULT_MAX_ROWS` (200) rows and `LLM_RESULT_MAX_CHARS` (20,000) characters, taken from the guarded query's result.
- At most `MAX_GENERATIONS` (3) `generate` calls per question.
- Timeouts:
  - 30 s per LLM call (`LLM_TIMEOUT_S`)
  - 5 s per statement (`STATEMENT_TIMEOUT_MS`)
  - 90 s per turn (`TURN_TIMEOUT_S`)
- Row caps:
  - display: 1,000 (`DISPLAY_ROW_CAP`)
  - export: 100,000 (`EXPORT_ROW_CAP`)
- SSE event names and payloads are exactly as in spec §7.6: `step`, `clarification`, `sql`, `result`, `analysis_delta`, `analysis`, `error`, `done`. Step names: `generating`, `checking`, `running`, `repairing`, `analyzing`.
- API keys: accepted only in POST/PATCH bodies, never returned, never logged, decrypted only inside `app/llm/`.
- Presets (spec §8.1):

  | Key | Label | Base URL | Share results by default |
  |---|---|---|---|
  | `zotgpt` | ZotGPT Gateway | `None` (staff enter it) | on |
  | `openai` | OpenAI | `https://api.openai.com/v1` | off |
  | `deepseek` | DeepSeek | `https://api.deepseek.com` | off |
  | `custom` | Custom (OpenAI-compatible) | `None` | off |
  | `fake` | Demo (scripted) | `None` | on |

  `fake` exists only when `HUB_ENABLE_FAKE_LLM=true`.
- Chat error codes (SSE `error.code`):

  | Code | When |
  |---|---|
  | `llm_auth_failed` | 401 |
  | `llm_rate_limited` | 429 |
  | `llm_unavailable` | timeout or connection error |
  | `llm_model_not_found` | 404 |
  | `llm_bad_request` | other 4xx |
  | `invalid_llm_reply` | still invalid after max generations |
  | `sql_rejected` | the guard still fails after max generations |
  | `query_failed` | execution still fails after max generations |
  | `turn_timeout` | the turn exceeded 90 s |
  | `profile_not_found` | the selected profile no longer exists |
  | `profile_missing_key` | the selected profile has no stored key |

## Review Focus

1. **The LLM wraps SQL in Markdown fences, adds a trailing `;`, or adds prose around the JSON.** Expected: fences and the semicolon are stripped and the first JSON object is extracted, with no wasted repair attempt. The tests are in Task 4 and Task 7.
2. **The provider rejects the key, rate-limits, times out, or the base URL is unreachable.** Expected: one `error` event with the specific code and a fix-it message, the turn logged with `kind = error`, and no 500. The test is in Task 8.
3. **A query returns 0 rows.** Expected: the local summary says `No matching records.` and the analyze prompt says the result is empty. The test is in Task 7.
4. **Result values that are not JSON-native** (`date`, `Decimal`, `None`). Expected: they serialize in SSE and in the analyze prompt (ISO dates; integral Decimals as ints). The test is in Task 5.
5. **The selected profile is deleted, or has no key, after the page loaded.** Expected: an `error` event `profile_not_found` / `profile_missing_key`, not a 500. A question over 2,000 characters gets a 422. The test is in Task 8.

### Task 5: Read-only executor and error sanitizer (A8)

**Files:**
- Create: `backend/app/chat/executor.py`, `backend/app/chat/error_sanitizer.py`, `backend/tests/chat/test_executor.py`, `backend/tests/chat/test_sanitizer.py`, `backend/tests/acceptance/test_sql_safety.py`

**Interfaces:**
- Produces:
  - `@dataclass QueryResult` with `columns: list[str]`, `rows: list[list[JsonValue]]`, `row_count: int`, `truncated: bool`
  - `to_json_value(v: object) -> JsonValue`: `date`/`datetime` → ISO string; integral `Decimal` → `int`, other `Decimal` → `float`; `None` passes through; other types → `str`
  - `run_readonly(sql: str, *, max_rows: int, engine: Engine | None = None) -> QueryResult`. Uses `get_chatbot_engine()` by default. Inside one transaction it runs `SET TRANSACTION READ ONLY` and `SET LOCAL statement_timeout = <settings.statement_timeout_ms>`, executes, calls `fetchmany(max_rows + 1)`, and sets `truncated` when there are more than `max_rows` rows. DB errors are re-raised unchanged.
  - `@dataclass SanitizedError` with `code: str` (SQLSTATE or `"unknown"`), `feedback: str` (for the LLM), `user_message: str`
  - `sanitize_db_error(exc: BaseException) -> SanitizedError`. Rules are in spec §7.5. The pass-through SQLSTATEs are `42601`, `42703`, `42883`, `42P01`, `42803`. `57014` gives `"the query was too slow; simplify it"`. Any other SQLSTATE gives `"<class description> (<sqlstate>); rewrite the query without relying on specific data values"`.

  - `execute` writes `step running`, then `result`;
  - `repair` writes `step repairing`;

  - `clarify` writes `clarification`;
  - `finalize` writes `error` (if `outcome == "error"`), then `done`.
- `generate` binds JSON mode unless `deps.json_mode is False`. If the provider rejects `response_format` and `json_mode is None`, it retries plain once and sets `json_mode_detected=False`. That fallback does not count as an attempt.
- `generate` catches provider errors with `map_llm_error`, sets `outcome = error`, and goes to `finalize` without repair.
